Choosing a method ​

A method is a quadruplet (discretizer, modeler, solver, parameter). This page maps out what can be combined with what, how a partial description gets completed, and how to inspect any one piece before you commit to it.

The four families ​

  • Discretizer: how the continuous problem is transcribed into a finite-dimensional one. Only :collocation exists today.

  • Modeler: how the resulting NLP is built: :adnlp (ADNLPModels, automatic differentiation) or :exa (ExaModels, SIMD-friendly and GPU-capable). :exa needs a problem written with @def, not with the functional API.

  • Solver: which NLP solver runs: :ipopt, :madnlp, :uno, :madncl, :knitro.

  • Parameter: the execution backend, :cpu or :gpu.

What is available ​

julia
julia> using OptimalControl

julia> methods()

(:collocation, :adnlp, :madncl, :cpu)
(:collocation, :adnlp, :knitro, :cpu)
(:collocation, :exa, :ipopt, :cpu)
(:collocation, :exa, :madnlp, :cpu)
(:collocation, :exa, :uno, :cpu)
(:collocation, :exa, :madncl, :cpu)
(:collocation, :exa, :knitro, :cpu)
(:collocation, :exa, :madnlp, :gpu)

There are 12 methods: every {adnlp, exa} × {ipopt, madnlp, uno, madncl, knitro} pair on :cpu (10), plus the two GPU-capable combinations :exa × {:madnlp, :madncl} on :gpu (2).

A problem to try them on ​

Every solve call on this page uses the same problem, the double integrator. Both modelers accept it as written:

The problem used on this page
julia
ocp = @def begin
    t ∈ [0, 1], time
    x = (q, v) ∈ R², state
    u ∈ R, control
    x(0) == [-1, 0]
    x(1) == [0, 0]
    ẋ(t) == [v(t), u(t)]
    0.5∫(u(t)^2) → min
end

Partial descriptions ​

solve(ocp, :madnlp) does not need the other three tokens: they are completed for you. Completion walks methods() from top to bottom and returns the first entry containing every token you gave:

julia
solve(ocp, :madnlp)   # → (:collocation, :adnlp, :madnlp, :cpu)
solve(ocp, :exa)      # → (:collocation, :exa,   :ipopt,  :cpu)
solve(ocp, :gpu)      # → (:collocation, :exa,   :madnlp, :gpu)

The first line of the display shows the completed method. For instance, with :exa:

julia> using NLPModelsIpopt

julia> sol = solve(ocp, :exa; print_level=0)

methods() is read top to bottom — the first match wins

Completion walks methods() from the top and returns the first entry containing every token you gave; nothing below it is ever reached. The default of a bare solve(ocp) is the same rule with no tokens: the very first entry.

julia
julia> first(methods())
(:collocation, :adnlp, :ipopt, :cpu)

All of these are equivalent:

julia
solve(ocp)                       # empty description → first(methods())
solve(ocp, :collocation)
solve(ocp, :adnlp)
solve(ocp, :ipopt)
solve(ocp, :cpu)
solve(ocp, :collocation, :adnlp)
solve(ocp, :collocation, :adnlp, :ipopt, :cpu)  # the complete description

Incompatible tokens ​

Completion fails whenever no method contains every token you gave. Two tokens of the same family can never match — :adnlp and :exa cannot describe one quadruplet — but neither can tokens of different families: :adnlp with :gpu has no match, since every :gpu method requires :exa. solve raises an error rather than silently picking one. What each solver needs installed ​

SolverLoad
:ipoptusing NLPModelsIpopt
:madnlpusing MadNLP
:unousing UnoSolver
:madnclusing MadNCL and using MadNLP (both)
:knitrousing NLPModelsKnitro (commercial licence required)
either on :gpuusing MadNLPGPU, using CUDA and using CUDSS, all three

Solving without the matching package loaded raises an ExtensionError naming the using statement to add; see Installation and GPU.

Understanding default values

(default: NotProvided) means that OptimalControl does not set the option, so the solver or modeler uses its own default. For instance, an Ipopt option shown with (default: NotProvided) takes Ipopt's default value. Only the options with an explicit default, such as (default: 1000) for Ipopt's max_iter, are set by OptimalControl.

These orders are theoretical, on a smooth solution. They can be checked on a problem whose solution is known:

Measuring the order on the LQ problem

For  ,  , and the cost   , the Riccati equation gives the optimal cost  . Each scheme solves the problem twice, on a grid of   steps and again on  : halving the step divides the error of a scheme of order by , so recovers the order.

julia
lq = @def begin
    t ∈ [0, 1], time
    x ∈ R, state
    u ∈ R, control
    x(0) == 1
    ẋ(t) == u(t)
    ∫(x(t)^2 + u(t)^2) → min
end

error_of(scheme, N) = abs(objective(solve(lq; scheme=scheme, grid_size=N, display=false)) - tanh(1))

for scheme in (:euler, :euler_implicit, :trapeze, :midpoint, :gauss_legendre_2, :gauss_legendre_3)
    e10, e20 = error_of(scheme, 10), error_of(scheme, 20)
    println(
        rpad(scheme, 18),
        "error N=10 ",
        rpad(round(e10; sigdigits=2), 9),
        "N=20 ",
        rpad(round(e20; sigdigits=2), 9),
        "observed order ",
        round(log2(e10 / e20); digits=1)
    )
end
euler             error N=10 0.029    N=20 0.014    observed order 1.0
euler_implicit    error N=10 0.029    N=20 0.015    observed order 1.0
trapeze           error N=10 0.0021   N=20 0.00054  observed order 1.9
midpoint          error N=10 0.00035  N=20 8.8e-5   observed order 2.0
gauss_legendre_2  error N=10 5.8e-8   N=20 3.6e-9   observed order 4.0
gauss_legendre_3  error N=10 4.2e-12  N=20 6.5e-14  observed order 6.0

Each line prints the scheme, its error on the two grids, and the observed order — matching the table above up to discretisation noise.

The higher-order schemes reach a given accuracy with far fewer steps, at a higher cost per step: a Gauss–Legendre scheme adds unknowns at the stages inside each step. The order is reached on a smooth solution. On a bang–bang control, the error is limited by the switching times, which fall between the points of the grid.

The grid is set by grid_size, the number of uniform steps (default 250), or by an explicit time_grid: the increasing times of the grid, from the initial to the final time, possibly non-uniform, to put more points where the solution varies fast. Here a grid twice as fine on the second half of the interval:

julia
grid = [range(0, 0.5, 21);          # 20 steps on the first half
        range(0.5, 1, 41)[2:end]]   # 40 steps on the second half — drop the duplicate t=0.5
sol_grid = solve(ocp; time_grid=grid, display=false)
length(time_grid(sol_grid)), objective(sol_grid)   # 61 points, objective ≈ 6
(61, 6.002344665885109)

Under :exa, no custom time_grid

time_grid works with :adnlp only: with :exa, it is not supported yet and currently fails with a DimensionMismatch (CTDirect#638).

Under :exa, no Gauss–Legendre scheme

:exa takes :trapeze, :midpoint, :euler and :euler_implicit, and the aliases of the last two (:euler_forward, :euler_backward, …). Both Gauss–Legendre schemes are available with :adnlp only:
